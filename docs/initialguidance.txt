PROJECT: 2D Multiplayer Animal Roleplay Game - CLIENT REPOSITORY
PRIMARY GOAL: Build the cross-platform game client for a 2D overhead multiplayer animal roleplay game.
LANGUAGE: C++
TARGET PLATFORMS: Linux, macOS, Windows
REPOSITORY ROLE: This repo owns rendering, input, camera, local UI, local asset loading, client-side presentation of world state, local prediction/smoothing, and all player-facing interaction surfaces.

==================================================
1. CLIENT MISSION
==================================================

This repository is the player-facing application for the game.

The client is responsible for:
- opening the game window
- handling input
- rendering the map, entities, and UI
- loading visual/audio assets
- sending player input and requests to the server
- receiving authoritative world updates from the server
- presenting smooth movement through interpolation/prediction
- displaying chat, names, interactions, and social feedback
- providing menus/settings/debug overlays

The client is NOT responsible for:
- deciding authoritative movement outcomes
- deciding whether an interaction succeeds
- deciding object ownership or world truth
- deciding final persistent player state
- deciding authoritative NPC/world state

Core rule:
CLIENT PRESENTS.
SERVER DECIDES.

The client may temporarily predict or smooth for responsiveness, but the server remains the source of truth for game state.

==================================================
2. DESIGN PRINCIPLES
==================================================

Design the client with these principles:

1. Presentation-first responsibility
- the client should focus on showing the game clearly and smoothly
- keep rendering/UI concerns separate from gameplay authority

2. Clear server boundary
- the client sends input/requests
- the client receives authoritative results
- avoid mixing visual assumptions with authority assumptions

3. Responsiveness without ownership
- use interpolation and optional local prediction
- do not let local presentation replace authoritative state

4. Simplicity first
- build a small, usable playable client before advanced polish

5. Data-driven content where practical
- maps, sprites, UI layout, and content references should be easy to evolve

6. Cross-platform stability
- keep platform-specific code isolated
- use portable libraries and build tooling

4. CLIENT ARCHITECTURE OVERVIEW
==================================================

Core runtime model:

- one game application
- one render loop
- fixed or semi-fixed local update path
- a client-side world representation
- a network connection to authoritative server
- local player input routed into outbound packets
- inbound state/events translated into visible presentation

High-level flow:

1. Client starts.
2. Window and renderer initialize.
3. Assets/config load.
4. Player enters menu or connect flow.
5. Client connects to server.
6. Handshake completes.
7. Client receives spawn/world state.
8. Player sends movement input and interaction requests.
9. Server sends authoritative updates/events.
10. Client updates visible state and UI.
11. Client smooths movement and shows chat/interactions.

7. CLIENT-SIDE DATA OWNERSHIP RULES
==================================================

The client owns:
- window state
- renderer state
- loaded textures/audio/fonts
- input state
- UI state
- local debug state
- interpolation buffers
- local settings/preferences

The client does NOT authoritatively own:
- true player positions
- final interaction outcomes
- object open/closed truth
- persistent gameplay progression
- authoritative NPC/world state

The client may temporarily maintain:
- predicted local movement presentation
- visual interpolation buffers
- local interaction target selection
- cached display data for smoother presentation

==================================================
8. RECOMMENDED UPDATE/FRAME FLOW
==================================================

A recommended high-level client frame flow:

1. Poll platform/input events
2. Update UI input focus and action mapping
3. Collect local gameplay intent
4. Send input/request packets to server
5. Process inbound network messages
6. Update client world presentation state
7. Run interpolation/prediction/reconciliation
8. Update camera
9. Render world
10. Render labels/UI/debug overlays
11. Present frame

Design note:
Keep render timing and network processing understandable. Avoid tightly coupling UI logic to packet handlers when possible.

==================================================
9. NETWORK PROTOCOL GUIDELINES FROM CLIENT PERSPECTIVE
==================================================

The client should follow the protocol contract defined by the server.

Initial packet usage from the client side:

Outbound:
- client hello or join request
- movement input
- interaction request
- chat send
- emote/status request later

Inbound:
- join accepted/rejected
- player spawn/despawn
- transform snapshots
- object state updates
- chat broadcasts
- interaction results
- server notifications

Guidelines:
- never assume local success before server reply for authoritative actions
- validate packet handling defensively
- log protocol issues in development builds
- separate packet parsing from UI concerns where practical

==================================================

To keep the client project achievable:

- do not overbuild the renderer early
- do not build a full custom UI framework unless the need becomes unavoidable
- do not add advanced animation/state machines before the multiplayer loop works
- do not add visual polish ahead of stable movement/chat/interactions
- do not assume every local feature should exist before server integration
- do not let client prediction become an authority system

Priority order:
1. clarity
2. responsiveness
3. correctness of protocol handling
4. usability
5. polish
6. performance optimization

==================================================
13. CODING STANDARDS FOR THE CLIENT AI AGENT
==================================================

Instructions for the coding agent working on the client repo:

- use modern C++ conservatively
- keep rendering, input, networking, and UI responsibilities separated
- favor small focused classes/files
- avoid premature abstraction
- keep asset loading straightforward
- keep network playback code understandable
- build the smallest usable feature first, then extend
- add debug visibility for complex behaviors like interpolation and input flow
- do not let presentation code silently assume authority

When implementing a new feature:
1. identify which client phase it belongs to
2. identify what server-facing protocol dependency it has
3. implement the minimal viable version
4. add clear logging/debug visibility
5. explain how it maps to server-authoritative behavior

When proposing refactors:
- explain why the current structure is insufficient
- preserve working gameplay loops where possible
- avoid rewriting stable systems for style alone

==================================================
15. TRUE FIRST SUCCESS CONDITION
==================================================

The first real proof that the client is succeeding is not:
- “the menus look polished”
- “the renderer supports everything”
- “the UI system is elegant”

The first real proof of success is:

“The client can open, connect to the server, send movement input, receive authoritative state, and display two players moving coherently in the same world.”

After that, the next true proof is:

“The client can also display chat, names, and at least one successful server-authorized interaction clearly and reliably.”
